# Does voting by many judges help? (2026-10-23)

Question from the sprint review: instead of one model answering a yes/no question once,
have many "agents" vote (for example the same model at different temperatures).

Short answer: **yes, but the votes must come from different models.** Averaging three
different local models' P(yes) was the best judge we measured. Votes from one model at
several temperatures, in several wordings, or with written reasoning helped little or not
at all. Voting on the *tests the model writes* (generation) traded coverage for precision
and is not worth using.

Data and scripts: `benchmarks/voting/` (copied from the session scratchpad).

## 1. Judge experiment

**Items.** 200 real yes/no questions the agent asked during the 2026-10-22 pilot, deduplicated:

- 142 "back-translation" questions (cascade gate: does this test check this requirement?)
- 58 "verify" questions (default mode: is this part what the person asked for?)
- 28 of them are perturbed copies (a stated number or direction changed) as extra negatives.

**Gold labels.** Two Claude labellers worked independently; one read the file forwards, the other backwards. They agreed on 204 of 209 items; I adjudicated the rest, and dropped 9 items (ambiguous or garbled perturbations). 112 are "yes" and 88 "no".

**Judges.** ornith-1.5:9b (today's model), qwen3.5:9b and gemma4. For each judge we recorded:

- P(yes) from token log-probabilities, in five wordings plus a "strict engineer" system prompt
- greedy answers
- ornith sampled 5–7 times at each of T = 0.3, 0.7, 1.0 and 1.5
- answers with written reasoning first (ornith ×5, qwen ×3, gemma ×3)

**Scoring.**

- Every configuration's decision threshold is chosen by 5-fold cross-validation (20 shuffles), so no configuration is scored on a threshold tuned on its own items.
- "Calls" means LLM calls per question.
- CI is a paired bootstrap of the accuracy difference against today's judge.

The full table, with 70+ configurations, is in `benchmarks/voting/final_all.txt`. There are also per-kind tables for back-translation and verify questions.

**What it shows**

- **Different models make different mistakes, so their average is the best judge.** The 3-model panel beats the best single model (qwen) by +0.05 [+0.005, +0.10]. It beats today's judge by +0.11.
  - On the cascade's own gate (back-translation questions, threshold 0.6), ornith alone passes **49%** of wrong tests. The panel passes **15%**, and gate accuracy goes from 0.78 to 0.90.
- **Majority votes of one model at temperature add little.** Its majority answer is about its greedy answer: false accepts stay at 34–48%.
  - What helps is keeping the *fraction* of "yes" votes and choosing a stricter threshold, which reaches 0.86–0.87.
  - That is not clearly worse than the panel on accuracy: +0.03 [−0.02, +0.08] in the panel's favour. But it accepts more wrong tests (17% vs 12%).
- **Rewording the question, or averaging wordings, does not help.** Each wording shifts the model's bias. Averaging them cancels nothing.
- **Asking for reasoning first hurts these 9B models.** qwen drops from 0.85 to 0.80, and gemma to 0.67. Voting over reasoned answers only gets back to about baseline, at 2–4 s per call instead of 0.3–1 s.
- **Cost.** The models do not fit in GPU memory together (ornith loads with a 262k context, 15 GB; even at 8k only one stays resident). A panel batch therefore pays about 4 s per model switch. The agent batches its yes/no questions per model so each switch happens once per batch.

**Caveats**

- 200 items, from the same 10 dev requests the agent has been tuned on.
- Labels come from Claude, not a human.
- The qwen+gemma pair was picked after seeing the data. The 3-model panel was the planned configuration, and it is the one the agent uses.

## 2. Generation experiment

**Setup**

- For 36 requirements (9 dev requests), the requirement → tests translation was sampled 7 times with ornith (T = 0, then 0.5 with different seeds) and 3 times with qwen.
- That produced 351 distinct tests, labelled the same way: two labellers agreed on 324, and I adjudicated the other 27.
- A strategy keeps a set of tests per requirement.

| Strategy | Precision | Requirements covered | Requirements with only correct tests | Requirements left empty |
|---|---|---|---|---|
| ornith, 1 sample (today) | 0.68 | 0.86 | 0.67 | 0.00 |
| ornith, keep tests in ≥ 2 of 3 samples | 0.69 | 0.81 | 0.61 | 0.06 |
| ornith, keep tests in ≥ 4 of 7 samples | 0.74 | 0.72 | 0.53 | 0.17 |
| tests proposed by both ornith and qwen | 0.58 | 0.81 | 0.44 | 0.08 |
| union of 7 ornith samples | 0.40 | 0.94 | 0.33 | 0.00 |

Voting on generated tests buys a little precision and costs a lot of coverage. Ornith's first (greedy) answer is already its best sample.

The better structure is to propose broadly and filter with a strong judge. The cascade already does this: the Python gates plus back-translation reject tests, and the loop asks again. The panel above makes that filter stronger.

I measured this offline. Each of the 351 tests was scored by each judge with the cascade's back-translation question, using threshold 0.6. The Python gates were not applied here. Data: `gen_judged.json` and `gen_filter.txt`.

| Strategy | Precision | Requirements covered | Requirements with only correct tests |
|---|---|---|---|
| 1 sample + ornith gate (today) | 0.74 | 0.83 | 0.64 |
| 1 sample + panel gate | 0.83 | 0.83 | 0.69 |
| 3 samples pooled + panel gate | 0.79 | 0.89 | 0.64 |
| 7 samples pooled + ornith gate | 0.50 | 0.92 | 0.42 |
| 7 samples pooled + panel gate | 0.76 | 0.92 | 0.56 |

So the panel is the better filter at every level of pooling. Pooling more samples raises coverage, but only a strong filter keeps the precision.

## 3. What changed in the agent

- `OllamaAgent(judges=[...])`: `p_yes` becomes the mean of the judges' P(yes).
- `p_yes_many` batches prompts per judge, so each model is loaded once per batch.
- The cascade gate, the cascade's tie-break ranking and the default mode's `rank_variants` all use the batch call.
- CLI options:
  - `--judges ornith-1.5:9b,qwen3.5:9b,gemma4:latest`: off by default, so today's behaviour is unchanged.
  - `--num-ctx N`
- `benchmarks/run.py --agent-args "..."` passes extra options through to every run.

## 4. End-to-end dev pilot (cascade vs cascade + panel)

**Setup**

- All 16 dev requests, 5 seeds each: 160 runs, alternating conditions seed by seed.
- Both conditions ran on code frozen at `benchmarks/voting/pilot2/code_snapshot` (SHA1SUMS inside), with `--num-ctx 8192`.
- Before the pilot, the blockers from the 2026-10-22 report were fixed:
  - the ball hang
  - the duplicate filter
  - roles for copies
  - the satisfiability, stand-in and zero-size gates
  - one-part designs left unverified
  - face pseudo-parts
- **Grading.** Blind, by two Claude graders per seed, each given the renders plus a measured part table. One rubric inconsistency was normalised: a modelled paper-towel roll counts as MINOR.
- Data: `benchmarks/voting/pilot2/`.

| | C: cascade, ornith judge | P: cascade + 3-model panel |
|---|---|---|
| Correct | 49 / 80 (61%) | 52 / 80 (65%) |
| Correct or minor ("good") | 55 / 80 | 58 / 80 |
| Called "verified" | 40 | 26 |
| **False pass** (verified but wrong) | **5 / 40 (12.5%)** | **1 / 26 (4%)** |
| False fail (good but not verified) | 20 / 55 (36%) | 33 / 58 (57%) |
| Timeouts / crashes | 0 | 0 |
| Median time per run | 115 s | 250 s |

**Paired by request and seed:** 75 ties, 4 where only P was good, and 1 where only C was good (sign test p = 0.38).

**Same 10 requests as yesterday's pilot:**
- Today's C is 82% correct (yesterday: 75%, with 3 requests timing out every run).
- P is 84%.

**What it shows**

- **The fixes moved the baseline more than the panel did.** There are no timeouts any more, and on yesterday's 10 requests the cascade went from 75% to 82% correct.
- **The panel makes "verified" more trustworthy, but at a price.**
  - False passes fell from 5 to 1. All 6 false passes in the pilot are one request: the dumbbell, whose "at each end" check passes with the balls under the bar. So the evidence is one failure mode, not a general rate.
  - The price is 13 more good designs left unverified, plus 2.2× the time.
  - This is the probe's trade-off showing up end to end. At the gate's 0.6 threshold the panel rejects 3× as many correct tests (6% vs 2%). One rejected correct test can leave a requirement "unverified".
- **Design quality is about the same.** The panel only judges tests, so it can only change the design indirectly.
- **The hard tier-3 requests (record stand, pet-bowl platform) fail in both conditions.** They need parts the library cannot place: a "slot for 20 records", or a board sized from the bowls.

**Recommended next steps** (details in `benchmarks/voting/pilot2/post_pilot_fixes.md`)

1. **Keep the panel, and fix its false rejections rather than its threshold.** When the panel rejects a test that ornith accepted, ask the panel about a reworded version, or let the translation loop propose again with that rejection as feedback. Alternatively, use the panel only as a veto, rejecting only when 2 of 3 judges are clearly negative.
2. **Validation layer.** Before "verified", ask the panel about Python's description of each part against the request (the default mode's back-translation). That is the check that would have caught the dumbbell.
3. **Bugs found in the pilot:**
   - "ends" arrangement with 3 copies drops one
   - the "edge" cue fires on "20 mm tall at its back edge"
   - the satisfiability gate abstains too often
   - size leak (egg 43 mm → cup inner diameter)
